认识HiveOS：让智能体在企业里持续工作

发布于2026-10-27更新于2026-10-27阅读 本文由AI辅助编写
蜂巢AI智能体

在自己的电脑上使用本地Agent，很多事情已经可以做得很顺：读文件、写脚本、安装依赖、运行程序，再调用模型决定下一步。电脑上的目录、工具和网络，让Agent有了实际动手的条件。

把这种方式交给一个企业里的许多员工，问题就变了。程序运行在哪里？谁准备环境、安装工具、分配资源？文件属于谁？员工关掉网页以后任务怎么办？Agent访问业务系统时，又代表哪个员工？

HiveOS，也就是蜂巢，从这些问题出发组织架构。可以先把它理解为：**企业在服务器上给每名员工的Agent配一台长期使用的“电脑”，再把这些电脑统一管理起来。**员工从网页提出任务，Agent在分配给自己的环境中执行，文件和方法留在那里，下一次继续使用。

“电脑”里到底有什么

这里说的电脑，指能够实际执行程序的环境。它有Linux用户空间、命令行、文件目录、可用的CPU和内存，可以运行Python、Node.js、命令行工具以及相应依赖。Agent在其中读取资料、生成文件、执行脚本、访问获准服务。

这台电脑也不等于大模型。模型负责理解和生成，Agent程序负责把模型响应接到文件、命令和工具上；执行环境则提供真正运行这些动作的地方。

例如，要求分析一份CSV时，模型可以决定先检查哪些字段，Agent随后在运行环境里启动Python读取文件、执行计算，再把结果带回模型继续组织报告。Python消耗的是这台执行环境的CPU和内存，模型推理则使用所配置模型服务的算力。两者不必在同一台机器上。

HiveOS为员工提供的就是这样的工作条件，并管理它与员工身份、任务和企业能力的关系。

用容器提供这台电脑

给每名员工买一台物理电脑，或者分别维护一台完整虚拟机，成本和管理工作都比较重。HiveOS的Docker部署方案用容器承载员工运行环境。

容器可以理解为宿主Linux系统中一个经过隔离的程序运行环境。它有自己的文件系统视图、进程和软件依赖，可以单独启动、停止，并限制CPU、内存等资源。一台服务器可以运行多个员工容器。

容器与虚拟机的重要区别是：容器共用宿主机的Linux内核，虚拟机通常运行自己的内核。因此，“给Agent配电脑”是对使用方式的比喻，底层没有为每个人复制一套完整硬件和操作系统。这个区别也决定了容器的隔离边界，不能把它当成绝对安全的独立物理机。容器的基本原理可参见Docker官方说明。

在HiveOS中，分配单位是员工：每名员工拥有自己的运行环境，Agent在里面执行工作。同一员工的新对话继续使用这套环境，不会每发一条消息就重新创建一台电脑。

图中展示Docker方案的职责与存储关系。容器独占使用不表示独占物理服务器；停止或重建容器，也不等于删除员工持久文件。

容器可以更换，员工文件要留下

长期工作环境最有价值的部分，是里面逐渐积累的东西：项目、资料、脚本、模板、个人Skill、配置和依赖。

如果这些内容只写在容器系统层里，重建容器时就会丢失。HiveOS把员工个人目录放到容器系统层之外，再挂载进运行环境。可以把它理解为：工作电脑可以重新安装，员工的资料盘继续接回来。

当前设计把个人资产集中放在员工用户主目录。项目代码、成果、个人技能和项目依赖放在这个持久目录中，系统软件则来自运行环境镜像，或在容器系统层中安装。

发生什么执行环境与文件怎样变化
一轮Agent任务结束本轮执行进程收尾，个人文件继续保留
新建另一个对话使用同一员工的运行环境和个人文件
停止运行环境进程停止，个人持久文件保留
重建运行环境容器系统层替换，重新挂载原个人目录

例如，某个项目的Python虚拟环境放在个人持久目录里，重建后文件仍在；通过系统包管理器临时安装在容器系统层里的软件，则需要重新准备。保留依赖清单和安装方法很重要，文件保留也不保证所有旧依赖在新环境里都能直接运行。

同一员工的多个对话共用文件，也共用容器安全边界。一个对话覆盖了文件，另一个对话就会看到修改后的内容。不同主题可以分开聊天，需要隔离的文件仍然要另外安排，不能把对话窗口当成另一台电脑。

平台怎样管理这些电脑

如果只给服务器上的每个人开一个容器，环境仍然需要人逐台维护。HiveOS在执行环境之外还有负责管理的组件。

**Core负责平台身份和工作记录。**它保存员工、任务、对话、资源分配和状态。员工发来一条消息，Core先创建本轮任务，核对执行条件，再交给相应的运行链路。任务过程回到平台保存，网页断线后可以重新读取。

**Runtime Manager负责宿主机上的实际操作。**它创建、启动、停止和重建员工容器，准备文件挂载，应用资源限制，并管理Agent执行进程。这些操作需要宿主机权限，因此集中在专门服务中，员工容器拿不到管理其他容器的Docker接口。

**员工运行环境负责真正干活。**里面运行Agent、脚本和工具。HiveOS当前接入Hive Pi、OpenCode等执行引擎：它们组织对话、调用模型和工具，平台提供外面的员工归属、生命周期与管理能力。

这使执行引擎与企业平台能够分别演进。选择某个引擎，影响它怎样推进任务；员工的持久文件、资源分配和平台身份则由HiveOS管理。切换引擎也不意味着两者的会话状态天然互通。

模型和业务系统走两条路

Agent在容器里执行程序，调用模型时则经过Model Gateway，也就是模型网关。企业在平台配置模型服务，网关按本轮任务的身份和路由连接上游，检查预算并记录调用用量。上游长期API Key不直接发给员工容器，任务使用临时模型访问身份。

访问企业工单、资产或其他业务系统，走的是另一条链路。脚本或工具直接调用相应业务接口；正式接入时，蜂巢提供限定目标系统的短期员工身份，由业务网关核验，再由业务方判断这个员工可以查询哪些数据、执行哪些动作。

可以把三类动作分开看：

准备执行环境：Core → Runtime Manager → 员工容器
请求模型推理：容器中的Agent → 模型网关 → 模型服务
办理具体业务：容器中的脚本或工具 → 业务网关 → 业务系统

模型网关管理模型访问，业务系统保留自己的业务权限。给员工分配某个系统、安装某项Skill，只解决平台能力是否可用的问题，不能代替业务系统中的账号关联和数据授权。

数据库保存平台身份、关系和任务状态，员工目录保存工作文件，对象存储保存资源包、备份和导出。把这些内容分开，才能在重建执行环境时保留员工资产，也能查清一个任务的状态与结果分别在哪里。

和在个人电脑上安装Agent有什么区别

本地Agent同样能够长期保存文件、安装工具、使用Skill，也可以通过脚本接入业务系统。这些能力本身并非HiveOS独有。

区别在于由谁提供工作环境，以及怎样把它交给企业员工持续使用：

需要处理的事个人电脑上的AgentHiveOS的组织方式
程序在哪里运行用户自己的电脑或自行配置的远程环境企业服务器上按员工分配的容器
文件和依赖由谁维护用户维护本机目录和软件环境平台准备运行环境，个人资产持久保存
多人怎样使用分别安装、配置账号和工具统一管理员工、资源、环境与企业能力
模型怎样配置用户自行准备模型服务与密钥平台配置模型，经网关按任务访问与计量
业务请求代表谁由用户自行安排凭据和接入方式正式接入使用短期员工身份，业务方核验权限
关闭使用界面后取决于所用工具和运行方式关闭网页不取消已提交任务，可稍后查看结果

这些差别可以通过其他工具组合出来。HiveOS做的是把它们组织成一个有员工归属和管理入口的平台。员工无需先在自己的电脑上安装整套Agent环境，企业也不必把所有人接到同一个共享业务身份上。

Skill则像放在工作电脑上的操作说明、脚本和模板。一次任务做好以后，把可复用方法留在员工目录或整理成企业资源，下一次继续使用。对话、定时任务、消息渠道和开放API提供不同入口，底层仍复用员工的执行环境及任务规则。

这台电脑也有边界

容器中的Agent能修改文件、执行程序，接入业务系统后还可能产生真实操作。限制CPU和内存可以约束资源使用，却不能证明每段代码和每次业务动作都正确；同一员工容器里的进程也没有彼此敌对的强隔离。

文件持久化不等于备份，取消任务不等于撤销已经发生的修改，恢复员工目录也不会自动回滚业务系统中的数据。它们分别需要备份、结果核验和业务恢复机制。

当前HiveOS仍面向单企业、单节点内网开发与受控验证，尚未生产就绪。“电脑在企业内网”也不表示模型推理一定本地运行：如果配置外部模型，发送给模型的资料仍会到达对应服务。

前面介绍的ACDL组织人和Agent的软件研发，HiveFlow连接反馈与交付；HiveOS提供员工实际使用的执行与管理环境。产品、架构和操作资料可继续查看蜂巢公开手册。
